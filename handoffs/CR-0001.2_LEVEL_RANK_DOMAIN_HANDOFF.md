## 2. Design conclusion

The implementation MUST distinguish:

```text
persisted historical state
from
new STRUCTURE intent
```

The new range rule is a **write-time/current-validation contract**, not a database
migration and not a read-time normalization rule.

### 2.1 Canonical write authority

A reusable Canonical Level/Rank domain validator must exist in the Canonical validation
layer.

Required semantics:

```text
level === null
→ valid for Draft shape subject to existing applicability rules

level !== null
→ integer AND 0 <= level <= 12

rank === null
→ valid for Draft shape subject to existing applicability rules

rank !== null
→ integer AND 0 <= rank <= 13
```

The validator must produce existing:

`CanonicalDomainError('DOMAIN_VALIDATION', ...)`

semantics.

Messages must identify:
- the invalid field;
- the permitted range.

No new error family is authorized.

### 2.2 New STRUCTURE submission

When `mutation.structure` is present, the entire submitted structure must satisfy the
new Level/Rank domain before persistence.

This applies equally to:
- Draft submissions;
- confirmed-block changes;
- ordinary Library PATCH;
- Carder selective write-back once it produces a Canonical structure mutation;
- External Source STRUCTURE Apply once it reaches Canonical mutation.

An out-of-range value must never become new durable Canonical state.

### 2.3 STRUCTURE-impacting password changes on historical data

Password/passcode participates in the existing STRUCTURE semantic block.

Therefore, on a legacy card whose persisted Level/Rank is out of range:

```text
password-only mutation
=
STRUCTURE-impacting mutation
```

and must not silently preserve the invalid historical Level/Rank as newly accepted
STRUCTURE intent.

A password-only STRUCTURE mutation against legacy invalid Level/Rank must fail until the
structural value is repaired in an accepted STRUCTURE submission.

This does not apply to unrelated TEXT, CLASSIFICATION, RELATIONS, provenance-only, or other
non-STRUCTURE mutations.

### 2.4 Historical compatibility

Do NOT apply the new range validator as an unconditional read-time or post-mutation
validation of every already-confirmed historical STRUCTURE.

The current service revalidates persisted confirmed blocks after mutations.
Adding the new Level/Rank range rule indiscriminately to that global path would violate
Scope by causing unrelated non-STRUCTURE mutations to fail for historical records.

Required behavior:

```text
historical Level 18
+ TEXT-only mutation
→ mutation may succeed
→ Level remains exactly 18

historical Rank 14
+ CLASSIFICATION-only mutation
→ mutation may succeed
→ Rank remains exactly 14
```

No automatic demotion, cleanup, clamp, null conversion, startup rewrite, or migration is
permitted.

### 2.5 New Review / Confirm

Review and new confirmation of STRUCTURE are current validation events.

A historical Draft or previously demoted STRUCTURE with out-of-range Level/Rank must:

```text
Review STRUCTURE
→ validation FAIL
→ DOMAIN_VALIDATION

Confirm STRUCTURE bypass attempt
→ rejected
→ HTTP 422 / DOMAIN_VALIDATION
```

A pre-contract STRUCTURE that is already CONFIRMED is not automatically demoted merely
because it is historical. However, once a new STRUCTURE Review/Confirm/reconfirmation is
attempted, the current domain applies.

Implementation must therefore add Level/Rank range enforcement to the **new confirmation
path** without retroactively making unrelated mutations fail solely because a previously
confirmed historical STRUCTURE is out of range.

## 3. Ordinary Library editor contract

### 3.1 Client bounds

For every Level control, including TOKEN Level:

```text
min = 0
max = 12
step = 1
```

For Rank:

```text
min = 0
max = 13
step = 1
```

Spinner/keyboard increment/decrement affordances must respect those bounds.

### 3.2 Blank and zero

Required intent:

```text
clear Level
→ null

clear Rank
→ null

Level 0
→ 0

Rank 0
→ 0
```

No `0 → null` coercion.

### 3.3 Direct invalid typed input

Typed out-of-range working input may remain temporarily visible, but:

- it must be represented as invalid local state;
- the user must be shown which field is invalid and the permitted range;
- it must not be silently clamped;
- it must not be submitted as valid Canonical STRUCTURE.

Examples:

```text
Level 18
must NOT silently become 12

Level -6
must NOT silently become 0

Rank 14
must NOT silently become 13
```

The exact component mechanism is implementation detail, but the observable behavior is
frozen.

### 3.4 Local Save gating

Client-side range validation must consider whether the attempted save is STRUCTURE-impacting.

For a new/edited STRUCTURE:

```text
dirty.structure == true
AND invalid Level/Rank
→ no PATCH
→ visible local validation error
```

For password edits:

```text
dirty.password == true
AND persisted/working STRUCTURE contains invalid historical Level/Rank
→ no PATCH until repaired
```

For unrelated historical edits:

```text
dirty.structure == false
dirty.password == false
TEXT / CLASSIFICATION / RELATIONS change only
→ do NOT block merely because historical Level/Rank is out of range
```

Historical out-of-range values must remain visibly exact in the editor until the user
repairs them.

### 3.5 No hidden client normalization

Do not modify `detailToWorkingForm()`, reload adoption, conflict reload, or ordinary
detail hydration in a way that rewrites historical numbers.

A loaded historical `18` must remain `18`, not `12`, `null`, or empty.

## 4. Carder selective write-back contract

No Carder protocol redesign is authorized.

No Carder production-side range-control change is required by this handoff provided the
server Canonical boundary prevents invalid persistence.

### 4.1 Boundary values

Carder selective write-back must permit, when structurally applicable:

- Level 0;
- Level 12;
- Rank 0;
- Rank 13.

Existing acknowledgement / confirmation-demotion semantics remain unchanged.

### 4.2 Invalid values

Carder write-back attempts that would submit:

- Level < 0;
- Level > 12;
- Rank < 0;
- Rank > 13;

must fail before durable Canonical persistence.

Expected server result when the request reaches Canonical mutation:

```text
HTTP 422
DOMAIN_VALIDATION
```

No revision advance and no partial mutation.

### 4.3 Historical compatibility through Carder

For a historical card with an out-of-range Level/Rank:

```text
Carder TEXT-only write-back
→ may succeed
→ historical Level/Rank remains byte/value-identical
→ no STRUCTURE mutation is synthesized solely because the value is legacy
```

If Carder changes the structural star/rank value:

```text
legacy 18 → 12
→ valid repair may persist

legacy 18 → 19
→ reject
```

Carder may not be used to preserve a newly submitted invalid structural value.

## 5. External Source STRUCTURE acceptance contract

Do not change:
- candidate schema version 1;
- normalizer version 2;
- adapter version;
- stored raw/source evidence;
- existing candidate append-only behavior.

The provider candidate may retain an observed safe integer outside the Canonical range as
source evidence.

The acceptance layer, not the normalizer history, must determine Canonical eligibility.

### 5.1 Preview

`workspace-server/src/external-sources/structure-result.ts` must use field-specific
validators:

```text
Level:
safe integer >= 0 AND <= 12

Rank:
safe integer >= 0 AND <= 13
```

Do not globally change the existing generic non-negative integer validator used by unrelated
fields such as printed stats, Pendulum Scale, or Link Rating.

Out-of-range Level/Rank candidate result:

```text
Preview decision:
INELIGIBLE

reason_codes includes:
STRUCTURE_VALUE_INVALID

resulting_structure:
must not be accepted as coherent eligible STRUCTURE
```

Preview must never claim READY or NO_OP for a candidate whose required applicable Level or
Rank is outside the frozen domain.

### 5.2 Apply

Apply internally re-evaluates Preview.

An out-of-range candidate must therefore be rejected before Canonical mutation using the
existing External STRUCTURE ineligible semantics.

The Canonical range validator remains the final authoritative fallback if any STRUCTURE
mutation reaches it.

No new External Source error family is required.

### 5.3 Valid boundaries

External Source Preview/Apply must continue to support:
- applicable Level 0;
- Level 12;
- applicable Rank 0;
- Rank 13.

No normalizer v3 and no migration are authorized.
